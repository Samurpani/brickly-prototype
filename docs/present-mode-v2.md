# Present Mode v2 — implementation and QA

> **Designer/developer experience brief:** start with [Present Mode — full product, design and development flow](present-mode-full-flow.md). This document is its technical implementation and QA companion, not the complete production specification.

Current immersive prototype implementation, verified against the modules and browser suite on **10 September 2026**. The recorded review supersedes the earlier free-browsing / no-map / live-configuration / drawer-shortlist direction. This is an implementation handoff, not evidence of production identity, approved production assets or backend delivery.

The user explicitly authorized a **clearly labelled illustrative spatial and neighbourhood demo** until a test project can be supplied later. Invented buildings, geometry, directions, outlooks and example places demonstrate interaction only; they are not approved project facts. **No project upload/import is implemented.**

## Visual direction

Inter, sage primary, Sandstone/Blackstone surfaces and OS tokens, with scene-specific rounded glass cards, a soft animated orb, conversational arrival and larger imagery. Clear focus outlines and touch controls remain. It does not inherit the uploaded document's black/yellow/serif styling. Reduced motion removes scene animations and shortens timed transitions; it does not skip unanswered questions.

The portfolio has Collection / Map views sharing filters and ordered multi-selection. Map view places **one selectable, filtered development list with filters on the left and geography on the right**, stacking on narrow screens. The map's duplicate legend is suppressed with `showLegend:false`; result buttons and markers toggle the same tour state. Filtering never deletes selected tour stops. Local SVG geometry uses no external tiles or tracking; prototype coordinates are explicitly illustrative. The left list remains usable if geometry fails. **This portfolio Malta map is unchanged.** Location now renders a separate, full-stage interactive schematic neighbourhood, not the old non-selecting locator/proximity overlay. Verify the portfolio geometry provenance, retained OpenStreetMap attribution and development coordinates before production; the new Location schematic has no geographic coordinates or basemap.

The tour retains numbered development progress, Next development and Review shortlist. Reps can revisit stops or the portfolio without losing selections. Units/Overview and specification controls have secondary drawers; request notes use a dialog. The shortlist is a dedicated full-screen stage. Fullscreen media is a separate protected `PMViewer` inside the buyer-safe shell, not the legacy CRM lightbox.

## Entry points

| Entry | Behaviour |
| --- | --- |
| Sidebar Present | Company intro → unanswered optional questions → Preparing developments → portfolio |
| Development detail Present | Same company intro/questions/preparation, then the selected development's opening and showroom Intro media view |
| Developments toolbar | Enter with no selection to choose from the portfolio, or present the ordered checkbox selection |
| Opportunity Present | Inherit linked Selection and known preferences. `qaPresent` resumes an open linked session if present; `PM.presentOpportunity(id)` starts a linked session |
| Appointment prep | Present to buyer when the existing prep card can be matched to an opportunity by its contact |
| Compare Present live | Inherit selected units, buyer context and lens; keep five selections but show no more than four columns |
| Explicit resume | Return to last buyer-facing screen; never bypass the sharing acknowledgement to restore a rep-only form |

Previously stored Compare `fin`/`lay`/`adds` values are not silently equated with `layout`/`preset`/`pack`. Unreviewed legacy items enter **Rep only · before screen sharing** review, not the buyer question scene. Original values remain in `legacy_config`; continuing acknowledges the Architect/Standard/Signature canonical default rather than silently translating earlier choices. Review also supports curated tour reorder/remove and resuming saved sessions. It is conditional, not a rep form shown during every buyer intro.

Known buyer types and explicit buyer tags are inherited. The legacy `buyerTypeFor` hash-based demo fallback is deliberately not treated as a known buyer preference. `presentPreferences` inherits explicit lens/style/finish choices, including previously answered no-preference choices. The answer flags distinguish answered defaults from unanswered questions; cancelling does not turn unanswered preferences into known ones. No contact or opportunity is required to begin.

## Screens

- **Company intro (screen `intro`):** silent company arrival from `PMData.company()` / `window.PM_COMPANY`; neutral “Your development collection” fallback with a generic decorative mark, not an invented developer identity. “Let’s begin” or the timed transition opens the first unanswered question. This is separate from the development's Intro media view inside the showroom.
- **Rep review (`review`):** conditional legacy/configuration and saved-session review before sharing, separate from buyer-safe setup. The rep sidebar Present launcher opens this picker when saved sessions exist; direct development entry still starts the buyer introduction.
- **Set the scene (`preflight`):** exactly one question at a time: buyer lens → style → finish. Selecting an answer automatically advances; there is no extra Continue step. Back retains answers and allows revisiting them. Skip / General and No preference are explicit answers. Inherited answered questions are omitted on forward progression.
- **Preferences (`preferences`):** revisits the same questions during a presentation and returns to the previous stage after completion (or Back from its first question). It changes visual preferences, not specifications or prices.
- **Preparing developments (`preparing`):** waits for first selected cover image, local map loading and a short motion interval, bounded by a 2.5-second fallback. Continue can bypass the wait; Back/Escape ends safely and invalidates stale transitions. This is local preparation, not AI/render generation. An existing tour proceeds to its first stop; an empty tour goes to the portfolio.
- **Development opening (`opening`):** silent and skippable, once per first visit to each development. Uses supplied approved logo metadata or the existing labelled development monogram.
- **S2 Portfolio:** select multiple development cards or map pins; shared filters; ordered selection strip with reorder/remove controls; Start tour. Filtered-out selections remain in the tour.
- **S3 Showroom:** opens every development on the new left-rail **Intro** (`ui.media:'intro'`) with **Units as the default panel**, with Overview still available. The rail includes Intro, **Project** (formerly Exterior; internal `exterior` state retained), conditional **Floors**, Lifestyle, Interiors, Gallery, Amenities, Timeline, optional Video and Location. Intro is the development hero/film view described below; Project is the illustrative site/building/elevation explorer, not a static exterior photo. Where supported, Floors provides full-level demo geometry and live prototype inventory inspection. Floors replaces the desktop side panel with its building/floor/unit inspector, while Units / Overview remains accessible in a drawer. Location occupies the full stage without that side panel. **Interiors and Gallery remain image grids with captions/provenance and fullscreen entry**, and Project imagery opens the gallery from the spatial scene. Amenities lists all supplied `d.amen` entries, not three teaser items. Timeline shows only supplied milestones, or completion alone with a missing-milestones explanation. Other narrative scenes retain their purpose-specific content. No Documents tab or ambiguous Focus action.
- **S4 Unit:** gallery/room thumbnails and fullscreen imagery; complete supplied residence facts with explicit unknowns; saved-specification plan; read-only canonical specification, swatches, price and request note. **Layout and style selectors are visual-only**, enabled only for matching approved assets. They do not edit saved configuration, finish pack, price or the actual saved-specification plan. No furniture editing or render production occurs here.
- **S5 Shortlist:** full-screen development groups with plan thumbnails, unit facts, saved specification/price, request notes, local buyer interest and privacy-preserving aggregate market counts. Select 2–4 available units or 2–3 introduced developments for comparison; continue to checkout even when comparison is unnecessary. Unavailable units remain read-only history.
- **S6/S7 Comparison:** one destination with Units / Developments switch, shared `PMData` rows, lens priorities, full amenity rows and Differences only. Unit headers identify their development, saved specification and plan/gallery entry. Missing facts remain dashes; unknowns and numeric ties do not produce a false best-value badge. Drill into a unit and return to the same comparison. Clear onward checkout action.
- **S8 Closing:** brand and thank-you screen; session saved immediately, even empty or anonymous. Explicit sharing-stopped acknowledgement before checkout.
- **S9 Checkout:** link opportunity/contact or create name-only contact + Qualified opportunity; prepare eligible shortlist; local preview and print; explicit simulated sends and real clipboard copy.
- **S10 Ready:** distinguish copied from simulated send; follow-up Custom Pack at Layout, preserving configurations and carrying visual preferences and notes for review. Existing drafts require Replace or Keep.

## Development Intro, illustrative Project, floors and Location

### Development Intro: hero or supplied film

- Intro is the initial development media view in the left rail, not the company arrival screen or the once-per-development skippable logo opening. Its hero uses the first exterior render `d.media.renders.ext[0].img`, falling back to `d.photo`, with the existing `UN_ASSET` prefix. It shows the development identity, location, completion and tagline, with Explore project and Explore residences actions.
- A supplied `d.media.video.url` resolving to HTTP(S) is shown over the hero with native `controls`, `muted`, `playsinline`, `autoplay` and `loop`, using the hero as its poster. With `prefers-reduced-motion: reduce`, **autoplay and loop are omitted**; playback remains user-controlled and muted initially. A video failure hides the failed film and restores the hero with “Film unavailable · showing project hero”; residence access remains available. No supplied film means the image hero, not an invented video or an upload prompt.
- Explore project opens **Project**, whose label replaces Exterior while retaining `ui.media:'exterior'` and the existing spatial action/state contract. Saved Intro and Project media can resume without translating `exterior` into a new state value.

### Project → building → floor → unit

- Project initially shows an invented two-building site selector: **Building A · Courtyard House** (`demo-a`) and **Building B · Garden House** (`demo-b`). Selecting either opens four distinct generated SVG facade elevations: North · Garden frontage, East · Arrival elevation, South · Courtyard frontage and West · Service elevation. Previous/Next side and side buttons switch drawings; this is **not true 3D, a model orbit or surveyed architecture**.
- `PMSpatial.project(developmentId)` reads current prototype inventory afresh. Unit IDs sorted alphabetically are assigned round-robin between the two demo buildings. Unit IDs, numeric floors and statuses are actual prototype records; **building assignment, footprints, room partitions, circulation, height, spacing and orientation are invented**. The same sorted mapping is used throughout the explorer, not asserted as a real unit property.
- **Floor availability:** `d.presentSpatial.floorNavigation === false` suppresses floor navigation regardless of inventory or the floor registry. Nonempty villa-only inventory (every unit's `type` matches `/\bvilla\b/i`) also suppresses it unless the setting is explicitly `true`; mixed inventory and substring-only matches such as “Villaggio” or “Villas” do not count as villa-only. Even `true` still requires numeric inventory floors or explicitly registered finite numeric floors; it never invents Ground or a range.
- Where floor navigation is allowed, each building lists the union of recorded numeric development floors (including numeric strings) plus finite numbers explicitly supplied in optional `DEV(id).floors`. No continuous floor range, missing levels or stock totals are inferred. Empty mapped levels remain visible and inspectable; zero registered units does not mean available or sold out. Units with missing/non-numeric floors remain in `unplacedUnitIds` and are disclosed, not placed on Ground.
- Unsupported developments have **no floor controls, interactive facade floor bands or Floors rail entry**. Stale `floors` media falls back to **Project** (`exterior`). The Project explorer, Units list and canonical residence drill-down remain available; suppressing floors does not remove units or change stock.
- Supported facade bands highlight and reveal their exact-level callout on **hover or keyboard focus**, without changing selection. **Click, tap, Enter or Space** delegates `sp-open-floor` for the selected building's exact registered level, clears the previous unit selection and sets `view:'plan'`, even when that building previously showed an outlook. From the full-level plan, opening a unit uses the canonical unit route; Back restores the originating Floors media, building, level, selected unit and viewport without changing saved specification or price.
- Floors shows a generated **whole-level SVG** with selectable unit footprints, shared circulation/core and a complete recorded-level silhouette. Floor chips and Higher/Lower floor traverse registered levels only. Status colours, text, counts and HTML unit buttons expose available, hold, reserved, sold and unknown stock. Only `status === 'available'` enables shortlisting; unavailable units can still be inspected in a read-only unit screen.
- The selected-unit inspector uses the host's price callback and canonical shortlist actions. Hidden/nonfinite prices become **Price on request**, never a fallback base price. Inspecting geometry or changing levels never edits `layout`, `preset`, `pack`, unit status, contractual price or shortlist membership; only the explicit eligible Add to shortlist action does the latter.
- Whole-level plans support button zoom, drag pan, pinch zoom and focused-plan keyboard arrows / + / − / 0 / Home. Zoom is clamped to 1–4×; 0/Home/Fit plan resets the viewport. Footprints also support Enter/Space and equivalent HTML buttons. Floor navigation remains in the stage; below 1100px the silhouette and selected-unit controls are also shown there, independent of the hidden desktop panel.
- **Views from this level · demo** switches to generated SVG outlooks varying by recorded floor, demo building and North/East/South/West direction. They explicitly say **Illustrative view · not an actual outlook**. Open fullscreen uses the protected `PMViewer`, with four direction items and `plan:false` (no plan drawing tools). Viewer browsing does not change the stored direction; Escape closes only the viewer and retains the floor state. No sightlines, actual views or real orientation are established.

### Location: local schematic neighbourhood

`PMNeighbourhood` renders the complete Location stage: original schematic streets, waterfront and development anchor; category filters; selectable markers and details; and an equivalent accessible places list. It contains **10 example POIs** across Transport, Education, Dining, Shopping, Health and Recreation: bus stop, ferry stop, school, café, bistro, market, grocery, clinic, garden and promenade. These are fictional examples, not real businesses, routes, coordinates, distances or journey recommendations. Only the development title is read from `DEV`; neither development proximity facts nor portfolio geography positions the schematic.

Mouse drag, wheel, two-pointer pinch, zoom buttons and keyboard arrows / + / − work locally, with 1–3.5× zoom. Home or Reset to development restores all categories, selects the development anchor and fits the map. Category changes clear a selected POI if it is no longer visible; marker and list selections stay synchronized. Clear place selection retains filter/viewport. No network requests, external tiles, routing or place-provider integration are added by either demonstrator.

### How to try

1. Open the [v2 prototype](../prototypes/Bricly_OS_Prototype_v2.html) through the existing local server. Start Present from a development, or use sidebar Present → company intro → unanswered questions → Preparing developments → portfolio → choose developments → Start tour. If saved sessions exist, the sidebar first offers rep review. The development opening is skippable; the showroom then starts on Intro with Units available.
2. Check the Intro hero or supplied film, native controls, reduced-motion behavior and film-failure hero fallback. Choose Explore project (or Project in the left rail), select Building A or B and cycle all four sides. Where supported, hover/focus a floor band, then click/tap or press Enter/Space to open that exact level's plan; Explore floors and the Floors rail remain alternate entries. Read About this demo mapping; use floor chips/Higher/Lower and inspect a footprint or unit button. For unsupported/villa-only developments, confirm there are no floor controls, bands or Floors rail and that Units still works.
3. Zoom/pan the whole-level plan, Explore/Inspect unit, then Back: the originating media, building, floor, selected unit and viewport return. Open Views from this level, switch direction, open fullscreen and press Escape. Revisit another building/development and resume a saved session to check independent memories.
4. Use Location filters, map markers and the places list; zoom before panning, then try wheel/pinch and the keyboard. Reset to development restores the initial view. Repeat at mobile/tablet widths and in the host's dark theme; the floor outline and actions remain in the stage.
5. Hide prices and inspect available versus unavailable stock; only eligible inventory can enter the canonical shortlist. End through the protected closing/sharing acknowledgement, then prepare a local preview: demo geometry, outlooks and POIs are not buyer-pack content.

## Data and integration boundaries

`PM` exposes the prototype integration API. `PM.enter`, `PM.presentOpportunity`, `PM.presentDevelopments`, `PM.resume`, `PM.price`, and `PM.reconcile` are the main entry points.

Local storage key: `bricly.present.v1`, version 1. It contains sessions, selections, prepared snapshots, linked demo records and inventory overrides. **Use demo data only.** This is not a production data store or authentication boundary.

- Selection contractual config: `layout`, `preset`, `pack`; style preference and request note stay separate.
- Session `preferences: {style, finish}` and item `visual_preference` describe presentation preferences, not purchased specifications. They never mutate canonical configuration or price. Existing imported configurations and notes are preserved.
- Session `ui.questionStep` and `ui.answers: {lens, style, finish}` track question progress/answer inheritance. `ui.preferencesSet` gates saving explicit preferences to the linked opportunity.
- Session `ui.unitPreview[unitId]` holds `{layout, style, index, imageKey, room}` for visual exploration. Room/image continuity is retained when a matching variant exists; otherwise the first supported image is selected. This state can survive local reload, but is not `item.config` and does not change the saved plan or price. Viewer ink is not stored here.
- Session `ui.spatial[developmentId]` holds `{developmentId, buildingId, floor, unitId, facadeIndex, direction, view, viewport, byBuilding}`. `buildingId` is `null` (site), `demo-a` or `demo-b`; `floor` is a recorded number or `null`; `unitId` is an existing mapped ID or `null`; `facadeIndex` is 0–3; `direction` is `north|east|south|west`; `view` is `plan|outlook`. `viewport:{x,y,zoom}` stores SVG viewBox origins in a 1000×660 space at 1–4× zoom. `byBuilding[buildingId]` independently remembers `{floor,unitId,facadeIndex,direction,view,viewport}`. Restored state is revalidated against inventory, not used to overwrite it.
- Session `ui.neighbourhood[developmentId]` holds `{category,poiId,viewport:{x,y,zoom}}`, initially `{category:'all',poiId:'development',viewport:{x:0.5,y:0.5,zoom:1}}`. `poiId` can be an example ID or `null`; x/y are normalized schematic centre coordinates, **not latitude/longitude**. Both explorer state maps survive save/resume and are initialized non-destructively in version-1 session migration; neither is canonical Selection or buyer output data.
- `openUnit` records `ui.unitReturn` (`compare`, `shortlist` or `showroom`) and `ui.unitMediaReturn` (the originating showroom media, otherwise `null`), then calls `PMSpatial.selectUnit` to synchronize the mapped building/floor/unit without losing the viewport. Back restores the originating route/media using the existing per-development/per-building state. Entering or revisiting a development through the tour opens Intro; this is distinct from unit Back or explicit session resume, which retain the originating/saved media. Selecting Floors reveals its remembered floor state when supported; stale unsupported `floors` media falls back to Project (`exterior`).
- Session `ui.tour` is the ordered development journey, separate from unit shortlisting. `ui.compareMode` selects units/developments within the single comparison route. Version-1 sessions migrate these fields non-destructively; the old `devcompare` route maps to `compare`.
- Linked opportunity extension `presentPreferences` stores explicit preferences and lens for subsequent sessions. Prepared snapshots include preferences; changing them invalidates prepared output.
- `is_shortlisted` distinguishes touched/configured units from deliverable items. Removing an item does not destroy its session configuration.
- Development-only interest is represented by a null unit ID.
- Unit item `interest` is independently stored as `unset`, `interested` or `favourite`; it is not inventory status, reservation intent or aggregate market demand.
- Session holds scope/order, lens, timestamps, viewed history, screen, price mode, return context and UI state. Closing captures a Selection snapshot.
- Custom Pack and Present use the same pure price calculation; Compare's existing rows and totals adapt to canonical configurations.
- The existing opportunity sidebar still expects display labels `fin`, `lay`, `adds`. These are retained as display-only aliases on the record boundary, not used as the contractual configuration.
- New contacts have blank optional phone/email and no assumed communication consent. They are not populated with invented delivery addresses.
- Custom Pack configuration edits update the linked Selection and matching Compare tray item. Request notes become each unit's modifier. A compatible preferred style seeds the existing pack; an incompatible style and any preferred finish remain explicit review requests, never a silent pack/price change. `presentPreferences` is also included in the seed. Existing drafts are never overwritten without confirmation.
- The existing v2 Compare checkout remains in place. Present has its own extended, session-aware S9/S10 checkout to support anonymous/empty sessions, development-only interest, hidden-price outputs and copy-vs-send semantics. Canonical configs are also preserved at the existing Compare prepare boundary. This is not a wholesale rewrite of unrelated Compare behaviour.

### Explorer integration APIs and lifecycle

The authoritative contracts are the module headers and current host integration, not a production import API:

- `PMSpatial` exports `ensure(developmentId,state)`, `project(developmentId)`, `renderStage(context)`, `renderPanel(context)`, `handleAction(action,arg,context)`, `selectUnit(developmentId,state,unitId)` and `mount(root,context,onChange)`. Context is `{developmentId,mode:'exterior'|'floors',state,selectedIds,priceFor,money}`; the user-facing Project label does not rename internal `exterior`. `ensure` requires and mutates the host-owned object; `project` returns a fresh inventory snapshot with `demo:true`, `hasFloors`, mapping disclosure, registered/available counts, unplaced IDs and building/floor records. `selectUnit` returns a boolean. `handleAction` returns `{handled,media?,openUnit?,shortlistUnit?,openViewer?}` for delegated `sp-*` actions; `sp-open-floor` validates the level against the current building, then returns `media:'floors'` with `view:'plan'`. Invalid levels are handled no-ops. `openViewer` contains `{items,index,title}`.
- `PMNeighbourhood` exports `ensure(developmentId,state)`, `render(context)`, `handleAction(action,arg,context)` and `mount(root,context,onChange)`. Context is `{developmentId,state}`; the host retains `ensure`'s returned object. `render` returns the **complete stage element**. Actions are `nb-category`, `nb-poi`, `nb-clear`, `nb-reset`, `nb-zoom-in` and `nb-zoom-out`; the result is `{handled:boolean}`.
- The host delegates clicks, owns canonical shortlist/price/availability checks and adds `root` / `onClose` when opening `PMViewer`. It disposes mounted explorer handlers before replacing markup or navigating away, and remounts Floors or Location only when no drawer is open. Mount callbacks **persist only, never rerender**: spatial gestures update the SVG viewBox and report completed gestures; neighbourhood changes update transforms and coalesce persistence per animation frame with `{developmentId,reason:'viewport'}` metadata.
- Focus is restored to equivalent controls after rerenders; spatial SVG Enter/Space activation is synthesized by the host. Explorer navigation keys are allowed through to their focused viewport; Escape remains host-owned, and active `PMViewer` keyboard handling takes precedence. Inventory reconciliation continues, while host DOM replacement is deferred for an active viewer as below.

## Shared Present / Compare facts and privacy

`PMData` is a DOM-free, non-persisting read boundary over existing host records/catalogues. Its exports are `unitRows`, `devRows`, `unitValue`, `unitNumeric`, `stats`, `marketInterest`, `projectGallery`, `unitGallery`, `plan`, `details`, `company`, `timeline` and `installCompareAdapters`. Returned text is plain text and must be escaped by the host. The sole trusted HTML result is the illustrative `plan().html` generated by the host's `unPlanSVG`.

- `unitRows(items, {lens, pricesHidden, priceFor, diffOnly})` accepts unit IDs or objects with `unit_id` / `unitId` / `id` and an explicit `config`. `devRows(devIds, {lens, pricesHidden, diffOnly})` accepts development IDs or names. Rows have `{key, group, label, values: string[], highlight, bestIndex?}`. They reuse `CMP_ROWS`, `CMP_GROUPS` and `CMP_LENSES`; they do not execute the legacy descriptor rendering closures. Lens aliases map `general` → `all`, `investment` → `investor`, `first_home` → `firsthome`, `second_home` → `secondhome`.
- Present passes its pure configured-price callback. `installCompareAdapters` runs **after** the host's earlier `CMP_ROWS` adapter loop and consumes explicit `cmpActivePlan` configurations, including the host's legacy-price fallback. **Existing `cmpDevColHtml` now also calls `PMData.devRows`** with the current lens/differences setting, renders the correct development column and uses `PMData.stats` for its From footer. Existing galleries and the five-item tray remain intact.
- `stats` distinguishes `registered` (all registered records), `available` (strictly available), and `total` (only a supplied nonnegative integer `attributes.total_units`, otherwise `null`). `from` and `avgPsqm` use **nonsold registered stock, including hold/reserved**, base prices and the arithmetic mean of valid per-unit price/area ratios. Registered stock is not asserted to be the full development size; empty or invalid numeric samples remain unknown.
- Unit rows cover configured price, €/m², comparison with the nonsold development average, demo yield/payment terms, residence facts, location and stock, plus orientation and parking. Development rows add supplied rental demand, management, schools, transport and coast distance. Unsupported facts are not invented. Unit gross yield uses the existing demo rent-per-m² table (fallback 16) and configured price; payment terms are readiness-based demo text. These are not live investment advice or verified offers.
- Full comparison amenities are the union of each development's `amen` strings and `attributes.amenityAvailability` keys. Explicit `false` means **Not included**; `true` or a listed amenity means **✓ Included**; absent in another development means **— Not listed**, not confirmed absence. This is separate from the showroom's full supplied amenity list.
- `pricesHidden:true` makes pricing keys `base`, `psqm`, `psqmVsAvg`, `yield` and `plan` read **On request** and removes numeric winners for those values. Differences-only compares displayed values. Generic detail extensions exclude price/yield/payment/rent/cost-like keys so they cannot bypass the dedicated pricing presentation.
- `marketInterest(unitId, opportunityId, contactId)` counts distinct other active local opportunity IDs containing that unit. It excludes the current opportunity, the current buyer's linked opportunities/contact IDs/names, and stages `Closed Won`, `Closed Lost` or `Lost` (case/whitespace normalized). The buyer-facing output is only a count labelled **aggregated prototype data, not a reservation or demand forecast**; other buyers' names, contact details and pipeline stages are not displayed. No live urgency, popularity feed or production privacy guarantee is claimed.

## Buyer safety

The shell makes the CRM inert and hides it visually and from accessibility navigation. It suppresses global toasts, blocks background route changes and isolates Escape handling. Late-added body overlays are also made inert. Tab is contained within the active shell/dialog; rerenders preserve matching focused fields/actions, and closing restores the originating control where available. Escape delegates to the viewer first, then closes a drawer before navigating back; an active buyer tour ends through the protected closing screen, not directly into the CRM.

Exiting native fullscreen does not remove the shell. The application cannot detect whether Zoom, Teams or another application is sharing a window. “Sharing stopped / screen turned back” is an explicit rep acknowledgement, not automatic detection.

Do not use Escape to exit an active buyer presentation to the CRM. End → closing → sharing acknowledgement → Save session only/checkout is the safe exit path.

### Protected gallery and plan viewer

`PMViewer.open({root, items, index, title, onClose, onIndex})` requires the connected `#pm-shell` as `root`. Items have unique stable nonempty string or finite numeric `key`, `url?`, `html?`, `caption?`, `provenance?`, `plan: boolean` and optional finite `northBearing`. Keys must remain stable per asset/version and distinct within a gallery. `onIndex(index, item)` updates the host's selected image/room. `PMViewer.close()`, `clear()`, `handleKey(event)` and the read-only `active` property complete the API.

- Gallery navigation, thumbnails, wheel/button/pinch zoom (1–12× fit), drag pan and Fit/reset work on images and plans. Plan-only Pan/Draw, Undo and Clear marks support freehand discussion. Fit resets the viewport without deleting marks. A north compass is shown only for supplied finite plan bearings, clockwise from the source's upward direction; an illustrative plan does not invent orientation.
- Ink uses normalized source coordinates, so it follows the plan through pan/zoom/resize. A second touch cancels an unfinished stroke before pinch; cancelled/lost pointer capture, blur and hidden-document transitions cancel incomplete gestures. Ink is **temporary, in memory only**: closing/reopening the same asset in the same presentation retains it; ending/closing the session clears it. It is never persisted, shared, printed/exported, sent to Custom Pack, or used to modify a plan/configuration.
- The viewer is a modal inside Present, not a body-level CRM overlay. It makes sibling shell content inert/aria-hidden, traps focus, blocks host pointer/keyboard delegation and restores focus on close. The host capture listener calls `PMViewer.handleKey` before its own Escape/Tab behavior. Escape closes only the viewer. Left/right browse; +/− zoom; 0 fits; P/D select plan modes; Control/Command+Z undoes; Shift+arrows pan when the viewport has focus.
- Inventory reconciliation and storage writes can continue while the viewer is open, but `render()` **does not replace the shell DOM while `PMViewer.active`**. Closing calls the host render to show deferred availability/price updates without interrupting a gesture or losing focus. Unavailable items are still removed from eligible comparison/preparation state immediately.
- Trusted app-generated SVG `html` takes precedence over `url` and is displayed in isolated image context, not inserted as arbitrary live markup. Invalid/unavailable sources show a fallback state. Close cleans up listeners, observers and object URLs; external detachment cleans up without reopening. The module contains Safari gesture-default guards, but this is **not Safari testing evidence**.

## Assets: intentionally honest fallbacks

Local project imagery is reused, but it is never presented as a matching configured-unit render merely because a filename resembles a finish.

### Concrete activation schemas and matcher rules

These are the actual optional prototype inputs, not a proposed production asset API. Use existing development/unit/catalogue IDs; filenames do not establish identity or approval. `PMData` asset/plan approval requires **`approved === true`**. Its `safeUrl` accepts nonempty HTTP(S) or relative URLs, rejecting whitespace/control characters, backslashes and other explicit schemes. Original relative project media is prefixed with `UN_ASSET`; supplied approved asset URLs are used as given. These client-side checks are not an asset authorization service.

**Gallery selection versus saved approval:** `PMData.unitGallery(item, {layout, style})` returns `{items, layouts, styles, layout, style}`. Each layout/style option has `{id, name, disabled}`. The saved layout's bare ID denotes its saved preset; another layout's bare ID denotes its first catalogue preset; additional presets use `layout:preset`. Only layouts/presets with approved assets for the saved pack and styles with assets for the resolved layout are enabled. The renderer passes these returned IDs back as preview state, never as a canonical edit.

If the requested layout has no assets, resolution prefers a layout supporting the requested style, then the first supported layout. If style cannot match, it uses the first supported catalogue style. Alternative layout/style and differing finish preferences are explicitly labelled; **the saved pack is retained throughout**. Unit and typology imagery have distinct provenance, with typology labelled “not unit-specific”. Images preserve room metadata; variant-aware keys include URL, development/unit/typology, layout, preset, pack/finish, style and variant identifiers so different variants are not collapsed merely for sharing a URL. Captions use `caption`, then `cap`, then `room`, then “Image”.

The separate host `PM.asset(item)` still determines saved `visual_state`: exact saved development/unit-or-typology, layout/preset/pack, chosen style if any, chosen finish if any, and a truthy URL. Unlike `unitGallery`, it does not require a catalogue style when none is selected or apply `safeUrl`; it is not a preview matcher. An approved alternative gallery visual therefore does **not** prove an approved saved-specification render. The older `developmentVisual` helper accepts only `kind:'interior'` and exact `finish`; the current Interiors grid uses the broader `PMData.projectGallery` matcher above.

**Known/unknown details:** the residence shows every base fact, supplied room names/areas/dimensions, features and allowed extra scalar facts. Missing orientation, parking and rooms are labelled **Not supplied**; absent other facts use **—**; rooms without sizes say **Dimensions not supplied**. Orientation text and a plan's north bearing are separate facts. Nothing is derived from demo SVG room geometry or image filenames.

Without approved mappings, the unit list remains the dependable entry, saved plans are explicitly **illustrative / not to scale / not a specification**, and saved visual state remains pending. A gallery with no eligible unit assets falls back to project context labelled “No approved unit visual for the saved finish pack”; no project imagery becomes an approved unit render. An unavailable project preference is labelled, and broken project-gallery images fall back to the project exterior with updated caption/provenance. No attached imagery means an explicit empty state. Style/finish cards are illustrative palettes, not generated residence previews. The existing four styles and three finish packs are reused; “ten styles” is not an approved asset catalogue. Real configuration, structural approval and bespoke production remain follow-up work outside the presentation.

### Future production replacement requirements — proposed adapter only

The metadata sketch in the `PMSpatial` header is a **future adapter design**, not a consumed global, upload form, file picker or accepted untrusted SVG input. Proposed project/facade/level/outlook overrides are metadata contracts, **not an upload UI**. They are separate from the already consumed `presentSpatial.floorNavigation` switch and `floors` registry, which only gate/register levels and do not replace demo geometry. Supplying a test project later will require implementation and validation before it can replace the demo. There is also **no `PM_NEIGHBOURHOODS` import or real-place adapter** in the current neighbourhood module.

- Proposed spatial metadata: `{version:1,developmentId,approved:true,provenance,buildings:[…]}`; each building has stable `id`, `name`, `footprint:number[][]`, approved/provenanced facade asset references, and floors with `id`, `elevation`, `label`, `unitIds`, `outline`, `units:[{unitId,polygon}]`, `core` and direction-specific outlook references with `assetId`, `captureElevation`, approval and provenance. This would replace `project()`/geometry adapters only after validation, not change the canonical unit schema.
- Require finite geometry coordinates, unique stable IDs, an explicit complete floor registry (including empty levels), exact development/building/floor/unit inventory membership and surveyed alignment. Supply vetted facade imagery, orientation/bearing metadata, approved level/direction outlooks and trusted, versioned asset URLs with rights/provenance. Real status and price must remain sourced from inventory and the host, not copied from geometry. Do not remove demo labels before approved replacements are actually connected; a future 3D model needs its own implementation and validation.
- Production Location needs verified development/POI coordinates, identities, categories, permission/licensing, provenance and maintenance dates. Verified routing/distance data and provider integration would be separate work; the decorative schematic paths must never become implied real routes or travel times.
- **Existing `window.PM_PLANS` remains independent and implemented:** it matches the unit's actual saved `layout`/optional `preset`/`pack` specification as documented above. It does not provide whole-building floor geometry. Demo floor, facade, direction and outlook state neither changes that matcher nor substitutes for an approved saved-specification plan.
- Keep future test-project geometry, contacts and POIs out of buyer packs unless a separately designed, approved export contract explicitly permits appropriate content. No uploaded test project is currently ingested. Today's demo geometry, building names, outlook SVGs, POIs and explorer viewport state are excluded from prepared snapshots, buyer preview/print content and Custom Pack configuration; neither demo export nor arbitrary asset passthrough has been added.

## Outputs, inventory and limitations

- Local preview links use the v2 URL plus `#shortlist=<id>`. They work only where the corresponding browser-profile storage exists; they are not public buyer links.
- Buyer previews read immutable prepared configuration/price snapshots and never rewrite the original session. Units that are now unavailable are excluded from preview.
- `prepare()` builds explicit canonical output fields rather than exporting session `ui`: selected eligible items, optional comparison/development IDs, buyer display name, lens/preferences and price/deliverable modes. Spatial/neighbourhood state, generated geometry/outlooks and example POIs never enter that output. The ordinary linked buyer name is not an export of unrelated contacts; existing aggregate-market privacy and hidden-price rules remain unchanged.
- Print uses the browser print dialog and its Save as PDF feature. There is no generated downloadable PDF service.
- Clipboard success records **Copied**. Permission failure records neither a copy nor a send.
- WhatsApp/email buttons in Present explicitly simulate a send. They do not contact anyone or prove delivery. Missing corresponding contact details disable the option.
- Unavailable units remain in history but are excluded from comparisons and preparation. Configuration, pricing or inventory changes invalidate prepared output before sharing.
- Local inventory/status/base-price changes are reconciled while the presentation is open (750 ms checks plus cross-tab inventory storage events), invalidating prepared output and pruning ineligible comparison units. During a viewer gesture, state reconciliation proceeds but visible host rerender waits for viewer close. `PM.simulateInventory(unitId, status)` is a rep-only testing hook, usable from a second local tab; it publishes a storage update. There is no real multi-rep backend feed.
- No live render production, second-screen presenter UI, casting, AI comparison narrative, voice-agent parsing, server persistence or public hosting is added.
